## 1. Executive summary

DRACO is further along than any of its documentation admits. The load-bearing achievement is real and enforced: every JSON definition under `src/main/resources/draco` regenerates its own Scala byte-for-byte (`DracoGenTest`), emits its own `.drake` surface (`DrakeGenTest`), and — for the plain-type, rule, and actor corpora — parses back to a JSON that survives a normalized round-trip (`DrakeParseTest`, ~525 tests, loss report down to 16 fields across 90 types). The framework validates its own foundation through the same rule engine it ships (`Completeness`, `SelfDeclaration`, `DerivationResolvable`, `CollectProblems` fired by a generated `Draco` actor). The recognizer principle from ch. 60 — a lax round-trip preserves mis-modeling; only an opinionated second projection rejects it — has repeatedly paid for itself (`RHSContext`, `Acpetion`, `Format(F)`).

The gap is between what the tree does and what anything *outside the tree* says it does. Every prose document is stale, several severely; the one Claude auto-loads (`DRACO.md`) still describes the `*Instance` triad, a flat `TypeDefinition`, `.rule` suffixes and `Generator.loadRuleType`, none of which exist. `AGENTS.md` claims to be a symlink and is a diverged older copy. `README.md` and `GETTING_STARTED.md` document `from-yaml`/`to-yaml` subcommands that were deleted with YAML in ch. 56. The `.drake` surface — 91 files and the whole parser/emitter — is mentioned in none of them. `CHANGELOG.md` stops at alpha.5 (June 3); ~25 git-records have accumulated since.

Beneath the docs, the code has a small number of concrete defects (listed in §4), one design hazard that I'd treat as the single most important technical finding (§3.2: parsed drake is not generation-safe for any value that isn't an application), a Generator that is not a pure function of its input, and a test suite that in a few places writes into `src/main` as a side effect and so can satisfy its own gate. None of these are architectural crises; all are fixable in a session or two. The architectural risks are of a different kind — a bus factor of one, a self-describing system where the most load-bearing type (`TypeName`) is about to change shape (#51), and a pair-programming process that has three documented instances of model-authored prose being laundered into design authority (ch. 69–70).

My recommended order of work is in §7. The short version: fix `DRACO.md` first (it is what steers every future session), close the four or five bugs, make parse output honest about what it demoted, stop tests writing source, then take #51 exactly as ch. 73 scoped it — the derivation edge only.

## 2. What is actually built (as-is architecture)

This section is here because none of the docs currently describe it accurately.

**Type system.** `DracoType` is a one-member trait (`val typeDefinition`). `TypeDefinition extends Aspects { val typeName }`, and `Aspects` is five slots: `dracoAspect` (superDomain, modules, extensible, derivation, elements, factory, globalElements, source, target), `domainAspect` (typeName self-loop or container pointer, elementTypeNames), `ruleAspect` (pattern, action), `actorAspect` (messageType, start, message, signal), `codecAspect` (discriminator). `TypeElement` is a sealed family of eleven kinds — Fixed, Mutable, Dynamic, Local, Parameter, Monadic, Condition, Action, Pattern, Variable, Factory — extending `Primal[Json]`, so `value` is a JSON node: either a host-opaque string or a single-key `{op: [operands]}` expression tree. `Domain[T]`, `Rule[T]`, `Actor[T]` are thin containers; `Actor[T] extends ExtensibleBehavior[T] with ActorType`.

**Companion convention.** Every generated companion is `object X extends App with DracoType { override lazy val typeDefinition = TypeLoader.loadType(TypeName(...)); lazy val dracoType = Type[X](typeDefinition); lazy val domainType = Domain[Container](typeDefinition); … }` plus derived codec, `apply`, `Null`. The lazy-val discipline is honoured throughout `src/main/scala/draco` (53 `App` companions; no eager top-level `val`s), with two exceptions noted in §4.

**Loading.** `TypeLoader.loadType → tryLoad → DefinitionPath.default.source(resourcePath) → readDefinition`. `DefinitionPath.hostRoots` is derived from `java.class.path`; each lookup probes every root; more than one hit is a hard error. A missing or unparseable JSON yields a typeName-only stub (not `Null`); `TypeLoader.rooted` injects `derivation = [draco.DracoType]` when empty (the ch. 68 "closed by inversion" of #38). `Generator.loadType` is a one-line delegate.

**Generator dispatch** (`src/mods/scala/draco/Generator.scala:1653–1738`). Entry normalizes with `TypeLoader.rooted` then `targetTypes` (the `{K,V}` → `Map[K,V]` rewrite lives only here). Order: `roleAspectCount >= 2` → `composedGlobal`; `!RuleAspect.isEmpty` → `ruleGlobal`; `!ActorAspect.isEmpty` → `actorGlobal`; `isDomain` (self-loop ∨ elementTypeNames ∨ source∧target) → `domainGlobal`; `isObjectOnly` → `objectGlobal`; else `typeGlobal`. That is six-way, not the five-way the README describes. A separate derivation-based `isActor` still exists and is used only to choose Pekko imports and to compute `isLeaf`.

**Codec derivation.** Discriminated-parent walk → `Codec.sub`; `modules.nonEmpty` → discriminated union; else a "simple" codec iff the type has own elements ∧ factory params ⊆ (own ∪ inherited) element names ∧ no uncodecable param. Codecs are therefore still *inferred* structurally. No JSON in any corpus carries a top-level `codecAspect` (verified programmatically over all 132 files); the field is defined on `Aspects.json` and referenced in two value strings, nothing more.

**DRAKE.** Emitter `Drake.emit`, parser `Drake.parse`, both in `src/mods/scala/draco/Drake.scala` (1019 lines) with `Expression.scala` (target-neutral shape accessors) and `DrakeCLI` (`emit | parse | check`, no `bin/` wrapper). The grammar as implemented: `type Name(T…) from ref…`, then keyword sections (`modules [ ]`, `extensible`, `elements`, `factory [vt]` + `parameters`/`body`, `globals`), then `domain pkg… Name` (+`super`, `types [ ]`), then `rule` (+`pattern`/`variables`/`conditions`, `action`), then `actor` (+`messageType`, `start`, `message`, `signal`). `codec` is rejected on both sides. Three local bracket rules: name lists always bracketed; keyword blocks never (bounded by admitted member keywords); openers (dyn-with-body, argument-that-is-an-application) bracket themselves. References are bare in own package, qualified elsewhere, case-bounded so the sequence needs no separator. Value types: `[T]`, `{T}`, `mut {T}`, `F(A,B)`, `A -> B`, tuples, and the neutral `{K,V}` map. The application surface (`fn parameters par x`, `par = name v`, chains via `.member parameters`, `[]`/`{}` defaults) is the *only* place the parser builds expression trees; every other value slot comes back as a raw string span.

**Outer layers.** `draco.generator.Generator[L]` is a one-field trait with no implementor; `draco.scalatarget.ScalaTarget` aliases the mods engine; `draco.rete.*` are marker traits; `draco.dreams.*` and `orion/*` are eight empty traits; `draco.format.{json,xml}` — `JSON`/`Value` are real, `XML` is a stub. `src/mods/scala/domains/` holds the World example (four media + `Sentient` + `World` with `Observable`, `Cartesian`, `Geodesy`), `Assembly`/`AssemblySpawner`/`AssemblyValidator`, and `pon/Pon.scala` (imperative PON parser/evaluator, no JSON twin). `src/main/scala/org/nexonix/**` (nine files, 354 lines) is a pre-draco toy RETE and empty mains referenced by nothing.

## 3. Design assessment

### 3.1 Strengths worth naming

The self-hosting gate is the framework's real asset: the framework's own source is a Generator fixture, and the three round-trip suites turn every metamodel change into a measured diff rather than an argument. "Presence, not name" (rule/actor-ness from aspect content), the composed multi-aspect emitter, rooted normalization at the entry boundary, and one loader with an explicit multi-root concept (`DefinitionPath`) are all clean eliminations of earlier accidental structure. Condition parameters being *derived* at emission (`Expression.rootNames`) rather than stored — because two compilers already enforce agreement — is exactly the kind of inference the ch. 58 model asks for. In DRAKE, the single arrow token, case-bounded reference sequences, brackets-on-the-opener, and "bare means own package" are principled and were each *measured* against the corpus before landing. The methodological lessons — Haskell test, latent/actual, recognizer vs specification, form-is-drake's-atoms-may-be-the-target's — are unusually well articulated for a one-person project and are written into commit messages.

### 3.2 The finding I'd rank first: parsed drake is not generation-safe, and nothing says so

`Drake.parse` builds expression trees only for the application surface. Every other value — lambdas, `if/then/else`, `->`, `*`, `==`, `!=`, `||`, tuples, dot paths — comes back as a *host-opaque string in Haskell form* (`Drake.scala:621–645`). `Generator.expression` passes strings through verbatim into Scala. So `format/json/Value.drake:12–13` (`\e a -> …`, `if … then … else`) parses to JSON that `DracoGenTest` would reject and that would not compile, and `DrakeCLI parse` prints it without a warning. The corpus is safe today only because the JSON twins were authored by hand and drake is emitter-first; the moment someone writes drake and parses it back to the corpus, the round-trip silently breaks. This is the #61 gap, but I'd frame it more sharply than the backlog does: until the parser builds trees for the operators both renderers already know, or marks demoted values, `parse` is a measurement tool, not an authoring path. Either fix is small; the lint ("no host-opaque string may contain a drake-form token") is smaller still and worth adding this week.

### 3.3 The Generator is not a pure function of its input

`chainHits`, `inheritedElementNames`, `loadDracoType`, and `actorKnowledge` all consult the classpath during emission (`Generator.scala:51–64, 111–120, 615–629, 1162–1183`), and `chainHits` catches `Throwable`. Under sbt (`fork := true`) the classpath is `target/classes`; under `bin/draco-gen` it is the fat JAR. An ancestor JSON edited but not yet compiled into either changes emission unpredictably. Every probe scans every root with `openStream()` and nothing is cached; generating `Draco` loads ~51 members. `generate` already accepts a `familyContext` for codecs — extending that to a loaded-family/`DefinitionPath` context and dropping the implicit lookups would fix reproducibility and cost.

### 3.4 Two competing notions of actor-ness

`hasActorBehavior` (`!ActorAspect.isEmpty`) drives dispatch; `isActor` (derivation reaches `ActorType`/`ExtensibleBehavior`) drives imports and `isLeaf`, and is *not* counted in `roleAspectCount`. `Draco.json` uses `actorAspect.messageType` with no `Actor` derivation; every mods actor uses `from draco Actor(T)` with no `messageType`. `AssemblyValidator.messageType` reads only the derivation, so a `Draco`-style actor fails validation. The `.dlt` (line 335) says messageType rides the aspect "rather than by an Actor(T) derivation" — the corpus hasn't caught up with the spec, and the parser accepts both silently.

### 3.5 Codec: inferred in code, declared in principle, for four months

Ch. 57 built the structural gate; ch. 58 decided codec is declared-not-inferred and deferred the migration to Generator[L]; the `.dlt` DIVERGENCES row records the intent. Nothing has moved. It's coherent as a deferral, but it leaves the metamodel with a fifth aspect that no type uses, an emitter/parser that reject the keyword, and a tripwire (#43) armed on a migration nobody has scheduled. Same story for the presence model (present-empty `rule`/`actor` still elide to absent), which is why `BodyElement.drake` and `ActorAspect.drake` sit in `authoredAhead`. Both are "settled but unimplemented" and should either get a date or be re-filed as explicitly post-Generator[L].

### 3.6 Core vs mods split has inverted

The ch. 43 north star was "`src/main` ⟺ definition-backed; bindings live in mods." In practice the entire engine (`Generator`, `GeneratorCLI`, `Drake`, `DrakeCLI`, `DomainBuilder`, `Assembly*`, `SourceContract`) is hand-written in mods, and core `TypeDictionary.apply` builds hollow members — `DomainBuilder.define` exists to work around it. This is not wrong, but the docs still describe mods as "speculative outer layers", and the invariant `DomainBuilder.validate` enforces ("declared member is JSON-backed") is violated by `Generated.scala` and `Codec.scala` in main. Either promote `DomainBuilder.define` into `TypeDictionary` or state plainly that mods *is* the engine tier.

### 3.7 DRAKE robustness

Layout is insignificant; token gluing is not (`mut{T}`, `[cursor`, `par =x`, `Iterator( (K,V) )` each parse to something else with no error). No line/column in any parse error; `takeText` throws `ArrayIndexOutOfBounds` at EOF; unknown or duplicate sections overwrite silently; a bare `pattern`/`start`/`from`/`types` inside a value truncates it. There is one *latent* ambiguity of the #60 kind not yet closed: a declared `par` whose default is an application is emitted unbracketed by `leafLines`, so the inner argument loop would swallow the next `par`. No corpus type hits it yet; it should be closed before one does. Two near-duplicate renderers (`Drake.expression`, `Generator.expression`) plus `SourceContract.ExpressionRenderer` will drift — `||` is already in two of the three and in no spec.
